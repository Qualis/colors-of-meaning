# Feature: Adopt uv for dependency management and fast environments

## Overview

Adopt **uv** (the Rust-based Python package/project manager) to replace the pip-freeze-based
`requirements.lock` (spec 030) with a principled, cross-platform lockfile, and to accelerate
the heavy tox environment rebuilds via the `tox-uv` plugin. Two concrete, felt problems
motivate this — this is not modernisation for its own sake:

1. **The 030 lock is a platform-frozen hack.** To stay portable, `requirements.lock`
   deliberately *excludes* the `nvidia-*`/`triton` CUDA stack and pins `torch` alone,
   relying on torch to re-pin its CUDA deps per platform. uv's first-class PyTorch support
   (`[tool.uv.sources]` + `[[tool.uv.index]]` with platform markers) lets us pin torch to an
   explicit CPU (or CUDA-by-marker) index and produce a genuine, universal `uv.lock` — fixing
   the hack properly.
2. **tox env rebuilds are slow.** `tox-recreate` rebuilds the full ML stack (torch et al.)
   on every run; the PR gate (spec 031) does this on every pull request. `tox-uv` swaps
   pip/virtualenv for uv, cutting env-build time dramatically.

**Honest tradeoff — this is a "recommend, with eyes open", not a slam-dunk.** The 030 lock
already works (green, reproducible). uv's benefits are real (clean cross-platform lock + fast
CI) but so are its costs: uv's project mode wants PEP 621 `[project]` metadata, so it entails
migrating `setup.cfg` → `pyproject.toml [project]`; and `tox-uv` requires **tox 4**, so it
entails a tox 3→4 upgrade across the repo's ~25 ad-hoc testenvs. This feature is worth doing
if the team values CI speed and lock cleanliness enough to absorb that migration.

**A safe subset is offered.** If the tox 3→4 / `[project]` migration is judged too disruptive,
**Option A** delivers most of the lock benefit alone: use `uv pip compile` (keeping `setup.cfg`,
tox 3, and the `PIP_CONSTRAINT` wiring) to regenerate `requirements.lock` as a real resolved
lock rather than a machine freeze. **Option B** (recommended target) is the full adoption:
`[project]` + `uv.lock` + torch index + `tox-uv`. The plan sequences B so it can stop at A.

Depends on spec 030 (whose lock/`PIP_CONSTRAINT` this supersedes) and touches spec 031 (the
PR gate's install step); best landed after spec 035 (lint/format config already in
`pyproject.toml`). No `src/` behaviour change.

## Core Concepts

- **uv project.** `pyproject.toml` with PEP 621 `[project]` metadata, `[tool.uv]` config, and
  a committed universal `uv.lock`.
- **Explicit torch index.** `[tool.uv.sources]` pins `torch`/`torchmetrics` to a named
  `[[tool.uv.index]]` (CPU by default, or CUDA gated by `sys_platform` marker), so the lock is
  correct on every platform without hand-excluding CUDA transitive pins.
- **tox-uv.** A tox 4 plugin that builds environments with uv instead of pip/virtualenv.

## User Stories

- As a maintainer, I want one committed cross-platform lock that resolves torch correctly
  everywhere, so I can delete the 030 CUDA-exclusion workaround.
- As a contributor, I want CI and local `tox` environments to build in seconds rather than
  many minutes, so the feedback loop (and the PR gate) is fast.
- As a maintainer, I want dependency and project metadata in one modern `pyproject.toml`, so
  there is a single source of truth.

## Acceptance Criteria

- [ ] Given the project, when dependencies are locked, then a committed `uv.lock` (Option B)
  or a `uv pip compile`-generated `requirements.lock` (Option A) exists and resolves the full
  closure reproducibly, with `torch` sourced from an explicit index — **no** hand-excluded
  `nvidia-*` pins required for portability.
- [ ] Given `tox`, when it runs, then it installs from the uv lock and is green at 100%
  coverage with all gates; under Option B, `tox-uv` builds the environments.
- [ ] Given Option B, when metadata is inspected, then `pyproject.toml [project]` carries the
  name, description, `python_requires`, dependencies, optional-dependencies (`testing`),
  entry points, and `setuptools_scm` versioning that `setup.cfg` held, and `python -m build`
  + `twine check` still pass.
- [ ] Given the CUDA/CPU split, when the lock is produced on and installed on a CPU-only CI
  runner, then torch installs from the CPU index without pulling an unsupported CUDA stack
  (the `pip check` "nvidia-cusparselt not supported on this platform" warning from 030 is
  gone).
- [ ] Given spec 031's PR gate and spec 030's `PIP_CONSTRAINT` wiring, when 036 lands, then
  they are updated to install via uv/the uv lock, and `requirements.lock` + `PIP_CONSTRAINT`
  are retired (Option B) or regenerated by uv (Option A); the audit-suppressions register and
  Dependabot config are updated for the new lock format.
- [ ] Given `uv`, when installed in CI, then its version is pinned.

## Hexagonal Layer Impact

Build/tooling only; **no `src/` layer changes**, no behaviour change, `pytest-archon` and
coverage unaffected. Files (Option B): `pyproject.toml` (`[project]`, `[tool.uv]`,
`[tool.uv.sources]`, `[[tool.uv.index]]`), `setup.cfg` (metadata migrated out; possibly
retired), `setup.py` (setuptools_scm shim — retire or keep), `tox.ini` (tox 4 syntax +
`tox-uv`; retire `PIP_CONSTRAINT`), `.github/workflows/pr-gate.yml` (install via uv),
`.github/dependabot.yml` (uv ecosystem), `docs/security/audit-suppressions.md`,
`CONTRIBUTING.rst`, `.claude/CLAUDE.md`, new `uv.lock`, retired `requirements.lock`.

## Open Questions

- **Option A vs B.** Recommend B (full: `[project]` + `uv.lock` + torch index + `tox-uv`) for
  the CI-speed and lock-cleanliness wins; fall back to A (`uv pip compile` only) if the tox
  3→4 / `[project]` migration is too disruptive. The PLAN sequences B to stop safely at A.
- **`tox-uv` requires tox 4 — verify first.** The repo pins `tox>=3.28.0,<4` and has ~25
  ad-hoc testenvs; the tox 3→4 upgrade is the load-bearing risk and is validated before the
  rest of B is committed.
- **CPU-only vs CUDA-by-marker torch.** The gate/CI is CPU-only; default the torch index to CPU
  (smaller, faster, no CUDA stack), optionally exposing a CUDA extra via `[tool.uv.sources]`
  markers for GPU users.
- **Keep `setup.py`/`setup.cfg`?** Under B, metadata moves to `[project]`; `setuptools_scm`
  versioning and the two console-script entry points must be reproduced in `pyproject.toml`.
  Decide whether to retire `setup.py`/`setup.cfg` entirely or leave a minimal shim.
- **Relationship to 030/031.** 036 supersedes 030's lock mechanism and edits 031's install
  step; both are called out so the change is understood as a deliberate evolution, not drift.
